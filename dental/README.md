# Dentora — نظام إدارة عيادات الأسنان

نظام متكامل لإدارة عيادة الأسنان: المرضى، مخطط الأسنان التفاعلي، المواعيد، خطط العلاج، الفواتير والمدفوعات،
الوصفات، المخبر، المخزون، المصروفات، التقارير، والفريق — بواجهة عربية حديثة (مع الإنجليزية)، ثيم فاتح،
يعمل **بدون إنترنت** على **ويندوز** (تطبيق مكتبي) و**أندرويد** (تطبيق APK) ومن أي متصفح.

> كل بيانات العيادة تُحفظ على الجهاز نفسه (IndexedDB)، ولا تُرسَل إلى أي خادم، ولا اشتراك سحابي. الاتصال الوحيد بالإنترنت هو
> تفعيل البرنامج بمفتاح ترخيص، مرة واحدة: يُرسَل فيه المفتاح ورقم الجهاز فقط. النسخ الاحتياطي ملف واحد بامتداد `.dentora`
> من الإعدادات ← النسخ الاحتياطي (أرشيف ZIP فيه كل الجداول وكل ملف مرفق على حدة، مع كلمة مرور اختيارية).

## المزايا
- **لوحة رئيسية**: مواعيد اليوم مع تغيير الحالة بضغطة، الإيرادات، التنبيهات (ديون متأخرة، مخزون منخفض، أعمال مخبر مستحقة)، آخر النشاطات.
- **المرضى**: ملف كامل (بيانات، تحسس وأمراض مزمنة بتنبيه واضح، تأمين، وسوم)، بحث عربي ذكي، أرشفة، صور وأشعة ومستندات، ملاحظات سريرية.
- **مخطط الأسنان (Odontogram)**: أسنان دائمة ولبنية بترقيم FDI، حالات لكل سطح (تسوس، حشوة، تاج، قلع، زرعة، علاج عصب، جسر…)، وضع تلوين سريع، سجل تاريخي، طباعة.
- **المواعيد**: عرض يوم/أسبوع/شهر/قائمة، أكثر من طبيب، كشف تعارض، تذكير عبر واتساب، حالات (مؤكد/وصل/قيد المعالجة/مكتمل/لم يحضر).
- **خطط العلاج والإجراءات**: قائمة أسعار قابلة للتعديل، خطة علاج لكل مريض مع الأسنان والأسطح، تحويل العمل المنجز إلى فاتورة بضغطة، طباعة عرض سعر.
- **الفواتير والمدفوعات**: فواتير أنيقة قابلة للطباعة بشعار العيادة، دفعات جزئية، رصيد المريض (الرصيد الدائن يُسدَّد تلقائياً من الفواتير المفتوحة)،
  إيصالات بأرقام متسلسلة (`R-000123`)، مبالغ مقرّبة إلى منازل عملة العيادة (0 أو 2 أو 3)، كشف حساب، تقرير الصندوق اليومي.
- **الوصفات**: قاعدة أدوية جاهزة، وصفة قابلة للطباعة ومشاركتها عبر واتساب.
- **المخبر**: طلبات التركيبات (تيجان، جسور، تقويم شفاف…) ومتابعة حالتها وتواريخ التسليم.
- **المخزون والمصروفات**: كميات وحد أدنى وتنبيهات انتهاء الصلاحية، مصروفات بالفئات والمقارنة بالفترة السابقة.
- **التقارير**: إيرادات ومصروفات وربح، حسب الطبيب والإجراء وطريقة الدفع، نمو المرضى، نسبة عدم الحضور، الذمم المستحقة، تصدير CSV.
- **الفريق والصلاحيات**: مدير / طبيب / مساعد / استقبال، دخول برمز PIN يُطلب عند كل تشغيل، قفل تلقائي، وقفل متصاعد بعد الأخطاء المتكررة.
- **الإعدادات**: بيانات العيادة والشعار، العملة والبلد وأسماء الأشهر، أيام وساعات العمل، نسخ احتياطي واستعادة (ملف `.dentora`
  يُتحقق منه بعد كتابته، بكلمة مرور AES-256-GCM اختيارية، والنسخ القديمة بصيغة `.json` ما زالت تُستعاد)، بيانات تجريبية، الترخيص،
  سياسة الخصوصية وشروط الاستخدام (يوافق عليها المدير في معالج الإعداد).

## التشغيل للتطوير
```bash
cd dental
npm install
npm run dev          # http://localhost:5173
npm test             # اختبارات vitest
npm run build        # الإنتاج → dist/
```

## النسخ المبيعة
| المنصة | الأمر | الناتج |
|---|---|---|
| ويندوز (مثبّت + نسخة محمولة) | `npm run electron:build` (على ويندوز، أو على لينكس مع wine) أو Actions ← **Dentora – Windows** | `release/Dentora-Setup-x.y.z.exe` و`release/Dentora-Portable-x.y.z.exe` |
| أندرويد (APK + AAB) | `npm run build && ./scripts/build-apk.sh` مع مفتاح التوقيع النهائي، أو Actions ← **Dentora – Android** | `android/build/Dentora.apk` و`android/build/Dentora.aab` |

- **التوقيع النهائي لأندرويد:** ملف APK الذي تشاركه وحزمة Google Play موقّعان بالمفتاح نفسه (`dentora-release.keystore`،
  بصمة SHA-256 تبدأ بـ `43:68:DD`). السكربت يرفض أي بناء بمفتاح آخر عند ضبط `DENTORA_EXPECTED_CERT_SHA256`.
  عند إنشاء التطبيق في Play Console اختر رفع مفتاحك أنت (PEPK) ليوقّع المتجر بالمفتاح نفسه. التفاصيل في `docs/ANDROID.md`.
- **سير العمل على GitHub:** يعمل بدفع وسم مثل `dentora-v1.0.1`، ويظهر في تبويب Actions للتشغيل اليدوي بعد دمج هذا الفرع في الفرع الرئيسي.
  بناء أندرويد يحتاج أسرار المفتاح (`ANDROID_KEYSTORE_BASE64`، `ANDROID_KEYSTORE_PASSWORD`، `ANDROID_KEY_ALIAS`).
- التفاصيل في `docs/WINDOWS.md` و`docs/ANDROID.md`.

## الترخيص والبيع
- يعمل النظام **7 أيام تجريبية** بكل المزايا، ثم ينتقل إلى **وضع القراءة فقط** حتى التفعيل.
- في **الإعدادات ← الترخيص** يظهر **رقم الجهاز** (8 أحرف). يرسله صاحب العيادة إليك، فتصنع له **رمز تفعيل موقّعاً**
  (112 خانة، يُلصق من الرسالة) يعمل على ذلك الجهاز فقط، مدى الحياة (الافتراضي، والسعر المعروض للعميل 59$ في `seller.ts`)
  أو لمدة تحددها، وبباقة standard أو pro.
- **مفتاح الترخيص (البيع دون رقم الجهاز):** من لوحة التحكم (`/admin` على https://dentora.raqeem.dev) تصدر مفتاحاً من 16 خانة
  (`XXXX-XXXX-XXXX-XXXX`) أو دفعة حتى 50 مفتاحاً لموزّع، بالباقة والمدة (مدى الحياة، أو سنة أو سنتان تبدآن من يوم التفعيل، أو
  حتى تاريخ)، دون أن تعرف رقم الجهاز. في الإصدار 1.1.0 فما بعده يلصقه صاحب العيادة في حقل الرمز نفسه في **الإعدادات ← الترخيص**
  والجهاز متصل بالإنترنت: يرسل التطبيق المفتاح ورقم الجهاز فقط إلى `https://dentora.raqeem.dev/api/activate`، فيرتبط المفتاح
  بهذا الجهاز ويعود رمز التفعيل الموقّع المعتاد، يتحقق منه التطبيق بمفتاحه العام كأي رمز آخر ثم يعمل دون إنترنت. ومع الإصدار
  1.0.0، أو جهاز لا يصل إلى الإنترنت، يفعّله الزبون من https://dentora.raqeem.dev/activate برقم جهازه ويلصق الرمز الناتج. المفتاح
  الواحد يعمل على جهاز واحد. العقد التقني في `docs/LICENCE-KEYS.md`، وطريقة البيع بالمفاتيح في [`server/README.md`](server/README.md).
- **الأمان:** الرموز موقّعة بتوقيع رقمي ECDSA P-256. **المفتاح الخاص** الذي يصنع الرموز (`license-private.jwk`) عندك وحدك
  (ونسخة منه سرٌّ في الـ Worker، يوقّع بها رموز اللوحة والمفاتيح)، ولا يوجد في المستودع ولا في التطبيق؛ التطبيق
  يحمل **المفتاح العام** فقط، فلا يستطيع أحد صنع رمز من التطبيق أو من الكود المصدري.
  احفظ `license-private.jwk` في مكانين آمنين: إن ضاع فلن تستطيع إصدار رموز لهذه النسخة من التطبيق.
- أداة التوليد خاصة بك وحدك (لا تُسلَّم للعميل أبداً):
  ```bash
  node scripts/code-generator.mjs <رقم-الجهاز>             # ترخيص مدى الحياة (السعر الحالي 59$)، الافتراضي
  node scripts/code-generator.mjs <رقم-الجهاز> standard|pro [YYYY-MM-DD | 1y | 2y | lifetime] [--key license-private.jwk]
  node scripts/code-generator.mjs verify <رقم-الجهاز> <الرمز>
  node scripts/code-generator.mjs reset <رقم-الجهاز>  # رمز إعادة تعيين رمز دخول المدير (إن نسيه المدير الوحيد)
  npx vite build --config vite.tools.config.ts      # صفحة HTML تعمل بلا إنترنت: dist-tools/code-generator.html
                                                    # (تطلب تحميل license-private.jwk مرة واحدة على جهازك، وفيها قسم لرموز الإعادة)
  ```
- **نسيان رمز الدخول:** إن نسي المدير الوحيد رمزه يرسل لك رقم الجهاز، فتصنع له **رمز إعادة** موقّعاً بالمفتاح نفسه يعمل على ذلك
  الجهاز اليوم وغداً ولمرة واحدة. يدخله من شاشة الدخول ← «نسيت رمز الدخول؟» ← «لدي رمز إعادة تعيين»، فيضع رمزاً جديداً.
  بيانات المرضى لا تُمس.
- **التواصل للتفعيل:** شاشة الترخيص تعرض زر «طلب عبر واتساب» برقم البائع (`src/features/settings/seller.ts`)، والرسالة
  جاهزة برقم الجهاز واسم العيادة (تحت رقم الجهاز مباشرة). يظهر في ويندوز والملف المشارَك مباشرة، ويختفي تلقائياً في نسخة مثبّتة من Google Play
  (سياسة الدفع في Play) فيبقى فيها رقم الجهاز وحقل الكود (الذي يقبل مفتاح الترخيص أيضاً) فقط. `showPurchaseInfo` يضبط ذلك: `'outside-play'` (الافتراضي)
  أو `'always'` أو `'never'`، وأي حقل فارغ (البريد، السعر) لا يظهر.
- لتغيير المفتاح (إن تسرّب المفتاح الخاص): `node scripts/code-generator.mjs keygen <ملف-جديد>`، ثم ضع المفتاح العام الجديد في
  `src/license/core.ts` وأصدر نسخة جديدة من التطبيق. الرموز القديمة لا تعمل في النسخة الجديدة. وحدّث السر `LICENSE_PRIVATE_JWK`
  بالملف الجديد وانشر الـ Worker من جديد (`server/README.md`)؛ بعدها لا تقبل رموزَ اللوحة والمفاتيح إلا النسخةُ الجديدة.

## خادم Cloudflare
الـ Worker `dentora-api` على https://dentora.raqeem.dev (ورابط workers.dev احتياطي). مصدره وإعداده وبيانات الحساب وطريقة النشر في
[`server/README.md`](server/README.md). النشر يحتاج `CLOUDFLARE_API_TOKEN` يضيفه صاحب الحساب، ولا يوضع في المستودع.
يخدم الـ Worker الموقع وتنزيلات أندرويد وويندوز ولوحة التحكم وصفحة التفعيل (`/activate`)، ومسار `POST /api/activate`
الذي يحوّل مفتاح الترخيص إلى رمز تفعيل: هو العنوان الوحيد الذي يرسل إليه التطبيق طلباً، ولا يرسله إلا عند التفعيل بمفتاح.

## التجربة والفحص
```bash
npm test                                   # اختبارات الوحدات (vitest)
VITE_QA=1 npx vite build --outDir /tmp/dist-tour   # بناء للفحص فقط: فيه window.__dentora (قاعدة البيانات) لسكربتات الفحص
QA_DIST=/tmp/dist-tour QA_PORT=4420 QA_SHOTS=qa-shots/tour node scripts/qa/tour.mjs --demo   # لقطات لكل الشاشات ببيانات تجريبية
QA_DIST=/tmp/dist-tour QA_PORT=4420 QA_SHOTS=qa-shots/shell node scripts/qa/shell.mjs         # CSP والصور وPDF والحوارات على اللمس
QA_DIST=/tmp/dist-tour xvfb-run -a node scripts/qa/electron.mjs                                # فحص تطبيق ويندوز (Electron)
QA_DIST=/tmp/dist-tour QA_PORT=4311 QA_SHOTS=qa-shots/licence-key node scripts/qa/licence-key.mjs   # التفعيل بمفتاح ترخيص (يحتاج license-private.jwk)
```
> نسخ البيع (`npm run build` وبرنامج ويندوز وملف أندرويد) **لا** تضبط `VITE_QA` أبداً، فلا يصل أحد إلى قاعدة البيانات من الصفحة.
> سكربتات الفحص ترفض أي بناء ليس فيه `window.__dentora` وتطبع الأمر الصحيح.
بيانات العيادة التجريبية (60 مريضاً، مواعيد، علاجات، فواتير…) تُحمَّل من **الإعدادات ← النسخ الاحتياطي ← بيانات تجريبية**.

## البنية
React 19 + TypeScript + Dexie (IndexedDB)، وأيقونات lucide-react، و`fflate` لضغط ملف النسخة الاحتياطية؛ دون مكتبات أخرى.
للصفحة سياسة أمان محتوى (CSP) في `index.html`، وهي نفسها التي يرسلها تطبيقا ويندوز وأندرويد: لا سكربت إلا من البرنامج نفسه ولا شيء من الإنترنت،
سوى طلب واحد يُسمح بإرساله إلى `https://dentora.raqeem.dev` (`connect-src`) هو تفعيل مفتاح الترخيص؛ وغلاف أندرويد يرفض كل طلب آخر إلى الشبكة.
انظر `docs/ARCHITECTURE.md`: التقنيات، نموذج البيانات، قواعد الواجهة، وطريقة التحقق.
